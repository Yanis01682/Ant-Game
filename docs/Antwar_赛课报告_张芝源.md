# Antwar 赛课结合作业报告：基于 Greedy-Forecast 的智能体设计

## 基本信息

- 最终提交 AI：`gf`
- 最终提交版本：`gf-v16`
- 比赛结果：公开榜单全局第 28 名
- 课内排名：人智导课程参加赛课结合学生中第 9 名
- 策略路线：`greedy-forecast`

## 摘要

这次 Antwar 作业中，我最终提交的版本是 `gf-v16`，公开榜单全局第 28 名，在人智导课程参加赛课结合的同学中排名第 9。这个版本没有走“把动作全交给大模型或者大搜索”的路线，而是把问题拆成了两层：一层用明确的节奏规则先处理比赛里最关键、最容易被普通搜索拖慢的动作，例如 `Lightning Storm` 的释放和安全 `Producer` 的建立；另一层再用基于官方 `forecast` 的小预算前瞻搜索，决定防御塔建造、升级、拆除和换位等细节。

我这样设计的原因很直接。Antwar 的局面变化并不是单一维度的：金币、塔位、蚂蚁推进、基地血量、超级武器冷却都在互相影响。单纯看当前回合收益，容易把钱花在看起来合理但节奏上很亏的动作上；如果把所有可能动作都完整搜索，又会遇到候选动作数量过大、实时决策预算有限的问题。因此 `gf-v16` 的核心不是“最复杂”，而是“把复杂度花在最值钱的地方”：用规则约束动作空间，用 `forecast` 看短中期真实后果，再用复盘数据不断修正策略节拍。

从迭代过程看，`gf-v16` 主要解决的是三个问题。第一，前面版本的生产塔路线要么几乎不会被实际选出来，要么建出来以后很快被拆掉，没有稳定转成中盘经济。第二，防御塔动作存在建拆和降级反复发生的现象，金币被来回消耗，后续塔科技和超武窗口都被压窄。第三，`Storm` 的释放不能只在“快死了”或者“快赢了”时触发，它需要成为中盘节奏的一部分，既负责清理兵线，也负责给己方推进争取空间。

## 工程结构与代码落点

我这次报告里想强调的，不只是“想法是什么”，还包括“想法落在哪个文件”。因为 Antwar 这类题目很容易出现一个问题：嘴上讲的是一个完整策略，真正实现时却被入口、包装层、运行时适配层和核心策略层拆散了。`gf-v16` 里我刻意把这些层次分开了。

```text
Ant-Game/
  AI/
    main.py
    ai.py
    common.py
    protocol.py
    ai_greedy/
      ai.py
      runtime.py
    SDK/
      backend/forecast.py
      utils/constants.py
  docs/
    版本记录.md
    比赛开发记录.md
    分数计算方法.txt
  analysis/
    replays/gf_v16_external_losses_8145343_8145362/
    gf_v16_external_losses_8145343_8145362_summary.json
  submissions/
    gf-v16.zip
```

这几层里，真正和 `gf-v16` 策略直接相关的是下面这些文件。

| 路径 | 作用 |
| --- | --- |
| `AI/main.py` | 平台入口，负责把选手 AI 接到赛题运行接口上 |
| `AI/ai.py` | 很薄的一层加载器，只负责把实现模块挂出来 |
| `AI/ai_greedy/ai.py` | `gf-v16` 的主策略，核心规则、评分和搜索都在这里 |
| `AI/ai_greedy/runtime.py` | 把平台状态转换成 greedy 策略可用的内部表示 |
| `SDK/backend/forecast.py` | 官方前瞻模拟器，负责克隆状态和向后推演 |
| `SDK/utils/constants.py` | 各类经济、塔、超武常量的来源 |
| `docs/版本记录.md` | 记录 `gf-v14` 到 `gf-v16` 的版本迭代依据 |
| `docs/比赛开发记录.md` | 记录平台复盘、失败样本和策略判断 |
| `analysis/replays/gf_v16_external_losses_8145343_8145362/` | 平台对局验证后整理的回放样本，不是官方最终结算数据 |
| `submissions/gf-v16.zip` | 最终提交包 |

最能说明“核心逻辑不在入口层，而在策略层”的，是 `AI/ai.py` 这个文件。它几乎只是把真正的实现模块加载出来：

```python
_IMPL_DIR = Path(__file__).with_name("ai_greedy")

AI = _load_impl("ai").AI
GreedySession = _load_impl("runtime").GreedySession
_to_greedy_info = _load_impl("runtime")._to_greedy_info
_to_sdk_operation = _load_impl("runtime")._to_sdk_operation
```

这说明最终对局里真正起作用的不是入口壳子，而是 `AI/ai_greedy/ai.py` 里的策略本体。也正因为入口层很薄，我后面写报告时才能把重点放到算法构建，而不是包装细节。

## 一、对题目的理解

### 1.1 这不是单纯的塔防题

如果只看表面，Antwar 很像一个对抗式塔防游戏：双方不断产蚁，我方建塔防守，对方也建塔防守。但真正写 AI 以后，我觉得它更像一个资源节奏题。原因有三点。

第一，防御动作本身会影响未来经济。建塔价格按场上塔数递增，升级和拆降也有明显成本。一个塔位是不是该建、什么时候升级、什么时候卖掉，不能只看这一回合能不能多杀一只蚂蚁，还要看这次花钱会不会把下一发超武、下一次关键升级或者生产塔窗口挤掉。

第二，进攻和防守不是两套互不相干的系统。杀掉对方蚂蚁能获得金币，己方蚂蚁到达敌方基地也能带来收益。也就是说，防住当前压力、把己方兵线往前推，本身就会改变后面的资源结构。只会防守的 AI 容易拖着拖着就变穷，只会冲进攻的 AI 又会被对方一波压穿。

第三，超级武器会放大节奏差。`Lightning Storm` 花费高、持续时间长、冷却也长。如果我方第一发 `Storm` 明显慢于对手，或者中盘 `Storm` 周期被塔的碎片化花钱拖住，那么差距不会只体现在一发技能上，而会体现在接下来几十回合的兵线、金币和塔阵上。

所以我没有把目标写成“每回合找一个局部最优动作”，而是把它理解成：

1. 先保证自己不在短期内被打穿。
2. 再让金币沉淀成有效资产，而不是在建拆之间蒸发。
3. 同时抓住 `Storm` 和 `Producer` 这两个对中盘节奏影响最大的支点。
4. 最后在局面进入收尾阶段时，把已有优势转化成敌方基地血量压力。

### 1.2 为什么选择 `greedy-forecast`

我在开发过程中并不是没有考虑过更重的搜索路线。仓库里也保留了 `mh-force` 这一类 MCTS/hybrid 方向，它更接近“启发式候选动作 + MCTS + 策略价值网络”的结构。从表达能力上看，这条路线当然有潜力，但比赛阶段我最后还是把主力放在 `gf` 上，主要有两个原因。

一方面，Antwar 的动作不是只有“建或者不建”这么简单。一个回合里可能涉及建塔、升级塔、降级回收、基地升级和多种超级武器；塔位又分布在多个候选点上。如果直接把大量组合都推给搜索，候选分支会很快膨胀。另一方面，比赛里很多关键动作本身带有强烈的节奏性质。例如明明已经进入可以争取中盘压力的阶段，却因为普通搜索觉得当前多建一座塔分数高一点，把 `Storm` 一直拖掉，这种问题不是把搜索预算机械调大就一定能解决。

因此我最后采用 `greedy-forecast`：

- `greedy` 不是指只看一步，而是指把高价值战术判断写得明确、动作空间收得足够小。
- `forecast` 负责把候选动作放进官方模拟器里向前推，看它在未来几十回合对基地安全、兵线压力和金币安全的影响。
- 对特别关键的动作，例如滚动 `Storm` 和安全生产塔转型，不完全依赖主搜索“顺便选到”，而是放到专门的战术层中处理。

这条路线对我来说比较务实。它能解释每个动作为什么出现，也能在平台回放里定位“是哪一层决策没有起作用”，方便后续迭代。

## 二、`gf-v16` 的整体结构

### 2.1 决策流程

`gf-v16` 的主循环可以概括成下面这条流水线：

```text
读取当前局面
    |
    |-- 判断当前领先、落后或均势
    |-- 统计兵线压力、基地血量、超武冷却、金币和塔状态
    |
优先战术层
    |
    |-- 可用时尝试关键 EMP/Storm 场景
    |-- 中盘尝试 rolling Storm
    |-- 落后或需要终结时尝试进攻型动作
    |-- 在满足安全条件时尝试 Producer pivot
    |
若没有高优先级动作
    |
forecast 搜索层
    |
    |-- 生成建塔、升级、拆降、换位等候选动作包
    |-- 对候选动作向前模拟
    |-- 用组合评价函数打分
    |-- 选择最有价值的动作，或保持空操作
```

我没有把所有动作完全混在一起选，是因为它们的性质并不相同。

- `Storm` 这种动作会直接改变之后一段时间的场面，错过窗口的代价很高。
- `Producer` 是经济路线的入口，如果只是把它当普通升级分支，早期版本里它会被主防线动作长期压住，理论上存在，实际上很少被选。
- 建塔、升级、拆塔这类动作更适合放进候选动作搜索，因为它们之间的组合很多，而且是否合适很依赖当前地图局面。

### 2.2 状态判断不是只看血量

在每回合开头，AI 会先根据双方基地血量判断当前大体是领先、落后还是均势，但它不会只看这个量。因为基地血量是一个滞后信号：有时候血量还没掉，敌方兵线已经压到门口；有时候血量暂时落后，但己方已经形成反推。

所以 `gf-v16` 还会结合下面这些信息：

- 场上活蚁数量和双方死亡计数，用于估计哪一边的兵线压力更大。
- 敌方蚂蚁距离己方基地的最近步数，用于估计短期危险程度。
- 我方金币和可回收金币，用于判断某个动作会不会把后续现金窗口锁死。
- 超级武器冷却和当前可支付能力，用于判断是否进入技能节奏点。
- 场上塔的类型和位置，用于判断防线是否已经有基础骨架，还是还在频繁换位。

这一步的作用是给后面的规则层和搜索层提供上下文。例如同样是拆一座塔，在第 60 回合且对方兵线还远时，通常没有必要；但在敌人已经贴到基地前、现金又不够救场时，它可能就是必要回收。

### 2.3 关键代码片段

`gf-v16` 在代码里其实已经把关键节奏写得很明确了。下面这段常量定义，基本就是版本骨架：

```python
SEARCH_BUDGET = 0.15
PRODUCER_UNLOCK_ROUND = 55
PRODUCER_MAX_TOWERS = 1
PRODUCER_PROTECT_UNTIL = 280
ROLLING_STORM_ROUND = 28
ROLLING_STORM_MIN_VALUE = 39.0
```

这几行对应的意思很直接。

- `SEARCH_BUDGET` 很小，说明不是重搜索，而是有限预算前瞻。
- `PRODUCER_UNLOCK_ROUND = 55` 说明生产塔不是开局就铺，而是中盘后才考虑。
- `PRODUCER_MAX_TOWERS = 1` 说明经济路线是受控的，不追求泛滥。
- `PRODUCER_PROTECT_UNTIL = 280` 说明生产塔一旦建出，会在中盘前半段得到保护。
- `ROLLING_STORM_ROUND = 28` 和 `ROLLING_STORM_MIN_VALUE = 39.0` 说明 `Storm` 不是只在终局用，而是从中盘开始就被当成节奏武器。

再看主回合的优先级顺序，`gf-v16` 的行为不是随机的，而是明确分层的：

```python
if self.front_state <= 0 and not self.reserve_depth:
    ops = self._try_emp(game_info)
    if ops:
        return ops

if not self.reserve_depth and self.current_round >= ROLLING_STORM_ROUND and self.front_state <= 0:
    ops = self._try_use_storm(game_info, False, pressure=True)
    if ops:
        return ops

if not self.reserve_depth and self._should_push_storm(game_info):
    ops = self._try_use_storm(game_info, self.current_round >= 260 or game_info.bases[1 - self.side].hp <= 8)
    if ops:
        return ops

if not self.reserve_depth and self._should_reserve_early_storm(game_info):
    return []

if not self.reserve_depth:
    ops = self._try_producer_pivot(game_info)
    if ops:
        return ops
```

这段顺序很能说明问题。它表示 `gf-v16` 不是先搜一遍再说，而是先把高优先级节奏动作处理掉，再把剩余局面交给普通搜索。也就是说，`Storm` 和 `Producer pivot` 不是附属功能，而是主线策略本身。

最后是评价函数。它不是单一的“杀得多就高分”，而是把生存、前线交换、现金、塔结构和兵线压力一起算进去：

```python
score += self._score_survival_window(info, ruin_round)
score += self._score_frontline_trades(info)
score += self._score_danger_window(ruin_round)
score += self._score_cash_safety(safe_gap)
score += self._score_tower_count(len(my_towers))
score += self._score_tower_investment(my_towers)
score += self._score_tower_spacing(my_towers)
score += self._score_tower_advancement(my_towers, info)
score += self._score_producer_setup(my_towers, info)
score += self._score_base_arc_coverage(my_towers, info)
score += self._score_hostile_distance_trace(info)
score += self._score_enemy_pressure(info)
```

这段能很清楚地说明 `gf-v16` 的“聪明”在哪里：它不是只看当前回合局部得失，而是把“中盘能不能活下来、钱能不能留住、塔阵能不能沉淀、兵线能不能推进”一起放进同一个评分框架里。

### 2.4 算法定义：规则优先的滚动前瞻搜索

如果用更算法化的语言来描述，`gf-v16` 可以看成一个“规则优先的滚动前瞻搜索算法”。我没有让 AI 一次性规划完整 512 回合，而是在每个回合重新读取当前状态，生成一批候选动作，对每个候选动作做短期模拟，然后选择当前最合适的一步。这种方式本质上接近 receding horizon control，也就是滚动时域控制：每次只认真评估接下来一段时间，但每回合都会根据最新局面重新决策。

整个算法可以写成下面这个流程：

```text
输入：当前游戏状态 s_t
输出：当前回合操作 a_t

1. 提取状态特征 F(s_t)
   包括基地血量、金币、塔结构、超武冷却、敌我蚂蚁数量、最近敌蚁距离等。

2. 执行规则优先层 R(s_t)
   如果满足 Storm、EMP、Producer pivot、收尾等高优先级条件，直接返回对应动作。

3. 若规则层没有动作，生成候选动作集合 A(s_t)
   包括建塔、升级、拆降回收、拆后重建、拆后升级和空操作。

4. 对每个候选动作 a 使用 forecast 得到未来状态轨迹
   s_t --a--> s'_{t+1} --> ... --> s'_{t+h}

5. 用评价函数 V(s'_{t:t+h}) 打分
   分数综合生存窗口、现金安全、塔结构、生产塔准备、兵线压力等项。

6. 选择评分最高的动作
   a_t = argmax V(s'_{t:t+h})
```

这套算法的重点不是“搜索深度很深”，而是“每一步搜索都在真实游戏规则里过一遍”。因为 Antwar 的很多后果有延迟，比如拆塔省出来的钱可能让下一发 `Storm` 变早，也可能让基地提前掉血；只看当前回合很难判断，所以我用 `forecast` 把候选动作放到未来窗口里比较。

### 2.5 状态特征设计

`gf-v16` 的状态特征不是神经网络自动学习出来的，而是根据游戏机制手工构造的。这一点比较传统，但可解释性强，也方便根据平台回放改策略。主要特征可以分成五类。

| 特征类别 | 具体内容 | 用途 |
| --- | --- | --- |
| 基地状态 | 我方/敌方基地血量，当前回合数 | 判断领先、落后、收尾和防守压力 |
| 经济状态 | 当前金币、可回收金币、建塔成本、升级成本 | 判断是否能开 `Storm`、是否能转 `Producer`、是否需要保留现金 |
| 防御塔状态 | 塔数量、塔类型、塔位置、是否高级塔、是否生产塔 | 判断防线结构和资产沉淀情况 |
| 兵线状态 | 活蚁数量、死亡计数、敌蚁到基地最近距离、贴近敌方基地的回合 | 判断攻防节奏和短期危险 |
| 超武状态 | `Storm`/`EMP` 等冷却、金币是否够释放 | 判断是否进入技能窗口 |

这些特征没有直接拼成一个向量喂给模型，而是分别进入规则判断和评价函数。这样做的好处是每个特征的作用比较清楚。例如“最近敌蚁距离”主要影响防守紧急程度，“高金币窗口”主要影响 `Storm` 和 `Producer` 的可执行性，“塔结构”主要影响搜索对建塔和升级动作的偏好。

### 2.6 候选动作生成算法

在主搜索层里，`gf-v16` 并不是简单枚举所有合法操作。完整枚举会产生太多低价值分支，所以我先把地图上的可操作点缩成一组 `ACTIONABLE_SITES`，再根据不同战术模式生成动作包。动作包比单动作更实用，因为 Antwar 经常需要“先回收，再升级”或者“先拆掉低价值塔，再在更合适的位置补塔”。

候选动作大致可以表示为：

```text
A(s) =
  Build(site)
  Upgrade(site, branch)
  Downgrade(site)
  DestroyBasic(site)
  Downgrade(site1) + Build(site2)
  DestroyBasic(site1) + Build(site2)
  Downgrade(site1) + Upgrade(site2, branch)
  DestroyBasic(site1) + Upgrade(site2, branch)
  Idle
```

其中 `branch` 表示升级分支，例如 `Basic -> Heavy/Mortar/Quick/Producer`，或者二级塔继续升到三级塔。这里我加了两个限制：

1. `Producer` 分支只在安全槽位开放，不允许前线任意基础塔转生产塔。
2. 回收类动作在早中期默认不开，除非已经进入较晚阶段、敌人贴脸、现金安全出现问题，或者进入终结场景。

这两个限制是实际复盘后加出来的。没有第一个限制，生产塔容易变成前线短命塔；没有第二个限制，AI 会倾向于过度调塔，造成 `churn`。

### 2.7 前瞻搜索和选择策略

候选动作生成以后，`gf-v16` 会把动作应用到克隆出来的游戏状态上，再用 `ForecastSimulator` 向后推进。为了满足平台运行时间，搜索预算被限制在很小的范围内：

```python
SEARCH_BUDGET = 0.15
MAX_NODE_COUNT = 20000
EVALUATION_HORIZON = 60
```

这里的 `EVALUATION_HORIZON = 60` 表示评价会关注未来一段回合内的结果，重点看基地是否掉血、敌蚁是否贴近、塔结构是否稳定，而不是只看动作执行当下。`SEARCH_BUDGET = 0.15` 则说明搜索必须轻量，不能为了多展开几层导致平台超时。

搜索节点里保存了当前模拟器状态、已选择的动作包、当前分数、最好后继分数和危险标记。每次扩展时，算法会优先扩展还没有充分展开、或者处于危险局面的节点。最后从根节点的子节点里选 `best_descendant` 最高的动作。如果最优动作和空操作差距很小，算法会偏向空操作，避免为了微弱收益乱花钱。

这也是 `gf-v16` 和普通贪心最大的不同：普通贪心可能只判断“当前建这个塔是不是分数最高”，而 `gf-v16` 会把建塔后的局面继续往后推，看它是否真的改善未来窗口。

### 2.8 评价函数的具体含义

报告前面给了评价函数的代码，这里把每一项的实际含义再写得更清楚一点。评价函数不是严格的数学最优模型，而是一个手工设计的启发式价值函数：

```text
V = V_survival
  + V_trade
  + V_cash
  + V_tower_count
  + V_tower_investment
  + V_tower_spacing
  + V_tower_advancement
  + V_producer_setup
  + V_base_arc
  + V_hostile_distance
  + V_enemy_pressure
  - Penalty_danger
  - Penalty_sunk_cost
```

各项含义如下。

| 项 | 含义 | 设计目的 |
| --- | --- | --- |
| `V_survival` | 未来窗口内基地能撑多久 | 防止为了赚钱或升级牺牲短期生存 |
| `V_trade` | 前线击杀和对方死亡情况 | 奖励能清兵、能换到经济的动作 |
| `V_cash` | 现金安全程度 | 避免把钱花光后错过关键超武或升级 |
| `V_tower_count` | 塔数量 | 保证基础防线规模 |
| `V_tower_investment` | 高级塔和生产塔的投资质量 | 防止只堆基础塔，鼓励有效升级 |
| `V_tower_spacing` | 塔之间的距离 | 避免防线过密和重复覆盖 |
| `V_tower_advancement` | 防线向前程度 | 鼓励不是只缩在基地旁防守 |
| `V_producer_setup` | 安全基础塔能否作为生产塔种子 | 让 `Producer` 路线有机会被主搜索铺垫 |
| `V_base_arc` | 基地正面扇区是否被覆盖 | 避免防线漏掉主要进攻方向 |
| `V_hostile_distance` | 敌方蚂蚁贴近基地的风险 | 惩罚敌蚁逼近 |
| `V_enemy_pressure` | 敌方兵线整体压力 | 让搜索区分“暂时没掉血”和“马上要被压住” |
| `Penalty_sunk_cost` | 拆降带来的折损 | 抑制频繁建拆 |

这种评价函数不是追求理论上的最优解，而是把我对游戏的几个关键判断压进同一个分数里：要活下来，要有钱，要有塔结构，要能推进，还要避免无意义折腾。

### 2.9 `Storm` 选点算法

`Storm` 不是固定落在某个写死的位置。`gf-v16` 会在合法地图点上尝试落点，用 `forecast` 比较释放前后的效果。压力型 `Storm` 的价值大致由以下因素组成：

- 我方基地血量是否改善。
- 敌方基地血量是否下降。
- 敌方蚂蚁死亡数是否增加。
- 落点周围是否覆盖足够多敌蚁。
- 落点是否靠近敌方基地或敌方半场。
- 如果落点太靠近自家基地且没有推进收益，会受到惩罚。

对应到代码里，压力型选点不是简单数敌蚁，而是把敌方基地距离、自家基地距离、敌蚁覆盖、未来掉血情况一起算：

```python
value = 0.0
value += 8.0 * max(0, trial.info.bases[self.side].hp - base_own_hp)
value += 30.0 * (base_enemy_hp - trial.info.bases[enemy].hp)
value += 12.0 * (trial.info.die_count[enemy] - base_enemy_deaths)

if enemy_base_dist <= 4:
    value += 18.0
elif enemy_base_dist <= 6:
    value += 8.0
else:
    value -= 16.0

if own_base_dist <= 3 and enemy_base_dist > 8:
    value -= 18.0
```

这段逻辑体现的是一个很实际的原则：`Storm` 不应该只用来救火。如果 90 金只是在自家门口拖一下，但没有推进和反打价值，它就很可能让后面经济更差；如果它能同时清兵、压敌方基地、给己方兵线开路，才更符合中盘节奏。

### 2.10 `Producer` 触发算法

`Producer` 的触发也不是单纯看“钱够不够”。它需要同时满足安全、经济和节奏三个条件：

```text
允许 Producer pivot 当且仅当：
1. 当前回合不早于 PRODUCER_FORCE_ROUND
2. 当前 Producer 数量小于上限
3. 最近敌蚁距离不小于安全阈值
4. 我方基地血量没有明显大幅落后
5. 如果还在 Storm 保护期，不能因为 Producer 抢掉第一发 Storm 预算
6. 安全槽位上存在 Basic，或者允许先补一个安全 Basic 种子
```

所以 `Producer` 的本质不是“经济越早越好”，而是“在不会破坏第一发 `Storm` 和基础防线的情况下，尽早建立一个能活到中盘的经济点”。这也解释了为什么 `gf-v16` 保持 `Producer` 上限为 1：当时平台复盘显示主要问题不是生产塔数量不够多，而是生产塔出现太晚、活得不够久、收益没有兑现。先把一个点做稳，比直接铺多个点更合理。

## 三、动作空间的构建

### 3.1 先收缩候选点，再讨论搜索

如果把所有合法塔位、所有升级分支、所有拆降组合都作为同等候选，搜索会很快变得不经济。`gf-v16` 的做法是先根据地图结构定义一组有意义的候选塔位，再按塔位族组织动作。

塔位族的思想很朴素：有些位置彼此很近，功能上互相替代。如果同一片区域随便堆满，既会造成防线分布差，也会让建塔成本越来越高。因此 AI 在建塔时会检查同族位置是否已经被占用，用这种方式避免候选动作一开始就走向无意义堆塔。

这样做的好处有两个。

1. 候选动作数量被压住，前瞻搜索能把预算花在更可能有价值的组合上。
2. 防线更容易形成空间结构，而不是哪里空就往哪里塞一座塔。

### 3.2 候选动作不是单动作，而是动作包

主搜索层生成的不是单纯的“建塔候选列表”，而是若干类动作包。大体包括：

- 在一个候选点建一座基础塔。
- 对已有塔做一次升级。
- 对基础塔做拆除回收。
- 对高级塔做降级回收。
- 先拆或降一座塔，再在另一个点建塔。
- 先拆或降一座塔，再把另一个塔升级。

这点很重要。因为 Antwar 的经济是耦合的，某些操作单独看不可行，组合起来才有意义。例如当前金币不够升级关键塔，但卖掉一座低价值塔后可以升级；如果搜索只看单动作，就会错过这种“资产换结构”的机会。

不过 `gf-v16` 并没有把所有回收组合一直开放。因为早期一旦允许过多 recycle 动作，AI 很容易出现一种不太像人打比赛的状态：这一回合换塔，下一回合又换回来，表面上一直在调结构，实际上把资源折损在返还比例里。为此我把回收型动作限制在更晚阶段或者紧急场景中，后面会单独说明。

### 3.3 为什么空操作也要作为候选

`gf-v16` 的搜索里保留了空操作，而且在动作收益只比空操作略高时，会倾向于不动。这件事看起来保守，但我觉得对这道题很必要。

很多局面不是“有钱就一定要花”。如果当前防线还能撑住，金币又正在接近下一次高价值动作窗口，那么硬做一个边际收益不高的建塔动作，可能会让后面的 `Storm`、升级或者 `Producer` 都慢一拍。空操作不是偷懒，而是承认“当前保留现金”本身有战略价值。

## 四、基于 `forecast` 的前瞻搜索

### 4.1 主搜索看什么

`gf-v16` 的主搜索使用了官方 `forecast` 相关状态和模拟器。每次生成候选动作后，我不是只用静态规则打分，而是把动作应用到模拟状态中，再向后推进一段回合，观察短中期结果。

在代码层面，这一层有几个明显特征：

- 搜索预算是小预算实时搜索，而不是无上限展开。
- 每个候选动作会先被应用，再通过模拟观察防线的生存窗口。
- 评价周期关注未来一段时间内基地是否掉血、敌方兵线是否贴近、现金是否陷入危险区。
- 在主搜索阶段，敌方基地血量会被规整到统一基线，避免“敌方刚好低血”把防守搜索带偏；真正的终结型动作由更上层的规则处理。

最后这一点对我很有帮助。因为“怎么守”和“怎么收尾”是两个目标。如果敌方基地已经很低血，搜索很容易为了几步后可能的终结，牺牲当下防线结构；而实际比赛里终结动作本身可以单独判断，不必让防守搜索在每个回合都被这个信号牵走。

### 4.2 评价函数的构成

我没有把评分写成一个只看杀敌数的函数，而是把它拆成多部分相加。用比较概括的形式可以写成：

```text
Score =
    生存窗口得分
  + 前线交换得分
  + 现金安全得分
  + 防御塔结构得分
  + 生产塔准备得分
  + 基地扇面覆盖得分
  + 敌方贴脸风险惩罚
  + 兵线压力修正
  - 危险局面惩罚
  - 无效回收沉没成本
```

其中我最重视的几项如下。

#### 4.2.1 生存窗口

如果一个动作让基地很快掉血，那么它即使短期多赚了一点金币，也不应该高分。`gf-v16` 会在模拟里记录基地第一次掉血以及继续恶化的回合，把“我还能稳多久”作为核心信号之一。

#### 4.2.2 现金安全

后期不是钱越少越好，也不是钱越多越好。钱多但一直不用，会错过压力；钱少到下一个必要动作都做不出来，也会失去主动权。评价函数里专门考虑了现金安全缺口，避免搜索把局面推到“眼前能守，下一步没钱”的状态。

#### 4.2.3 防御塔投资质量

塔数本身不是越多越强。建造价格随塔数上涨，如果塔只是基础塔反复堆着，可能很快就变成低效投资。所以评价里同时考虑：

- 塔数量。
- 建塔总投入。
- 二级和三级塔的价值。
- `Heavy+`、`Quick+` 这类高效塔分支的额外价值。
- 塔之间是不是挤得太近。
- 防线是不是向前推进并覆盖了基地正面扇区。

这样做的目的是让 AI 不只追求“多一个塔”，而是追求“更像一条防线”。

#### 4.2.4 回收沉没成本

拆塔和降级并不是免费重排。返还比例会造成折损，而且新动作也会重新消耗金币。`gf-v16` 在搜索评价中显式给回收行为记沉没成本，使“为了微小局部收益反复折腾”变得不划算。

### 4.3 这套搜索为什么适合本题

我认为这套搜索的价值不在于它能穷举，而在于它能把启发式动作放进游戏真实规则里验一下。比如某个升级动作从静态角度看很诱人，但一模拟发现之后十几回合基地压力更大，那它就不应该只凭“塔变高级了”拿高分。反过来，有些动作眼前没有漂亮数字，却能把基地安全窗口拉长、让后面有钱开 `Storm`，这种动作也应该被保留下来。

所以 `gf-v16` 不是“规则”和“搜索”二选一，而是先用规则把问题缩到能搜，再用模拟防止规则凭感觉过拟合。

## 五、`gf-v16` 的关键策略

### 5.1 防御塔：优先形成骨架，而不是不断换姿势

早期版本里我比较容易被一个现象骗到：动作看起来很多，塔也一直在变，但中盘并没有真的更强。后来复盘时我发现，问题不一定是某个塔型选错，而是“建、拆、降、再建”的频率太高。每一次局部修正都像有理由，叠起来却把金币窗口切碎了。

所以 `gf-v16` 的防御塔策略更强调三件事。

第一，先让基础防线位置稳定下来。候选塔位经过筛选，同一区域不会无节制堆塔。这样防线不会因为单回合局部最优不断变形。

第二，评价高质量升级，而不是只奖励塔数。高效高级塔需要被搜索看见它的长期价值，否则 AI 会更愿意保留一堆便宜动作。

第三，回收不是默认动作，而是有条件动作。只有局面进入一定阶段，或者确实存在近危、现金缺口和终结压力时，才开放更积极的 recycle 组合。

这套思路不追求“每个回合都把塔阵重新优化一遍”，而是让塔阵形成可继续投资的骨架。

### 5.2 `Producer`：从搜索里的可选项，变成受控的经济转折点

我在这次比赛里对 `Producer` 的认识变化很明显。

一开始我把它当成普通升级分支的一种：搜索觉得合适就升级，不合适就算了。后来平台对局复盘说明，这样做基本等于没有生产塔路线。因为早中期主防线动作更容易马上在评分上体现收益，`Producer` 的长期价值很难自己从一堆候选动作里冒出来。

但另一种极端也不行。生产塔不是越多越好，过早或者过多转经济，会直接削弱当前防线，让经济还没滚起来就先崩掉。因此 `gf-v16` 对 `Producer` 做的是“窄而明确”的策略。

#### 5.2.1 只在安全槽位上考虑生产塔

我把 `Producer` 的建立限制在一组偏后排、侧翼或者相对安全的位置，而不是让任何基础塔都随便转经济。这样做的原因很简单：生产塔本身不承担主要火力，如果把它放在正面核心火力位，就等于自己把防线挖掉一块；如果位置太靠前，它还容易变成短命资产。

#### 5.2.2 用 pivot 打开实际转型

`gf-v16` 中的生产塔不只是“搜索可以升级到 Producer”。在满足条件时，会先尝试一个专门的 `Producer pivot`：

- 回合进入中盘准备区后才考虑。
- 场上还没有生产塔时才考虑。
- 敌方兵线不能已经贴脸。
- 自己血量不能处在明显大幅落后状态。
- 第一发重要 `Storm` 预算没有被生产塔抢掉。

如果安全位已经有基础塔，并且金币足够，就把这个基础塔转成 `Producer`。如果还没有基础塔种子，在塔数和预算允许时，先在安全位补出一个基础塔，为后续转型做准备。

这一步的意义是：生产塔路线不能永远停留在“搜索理论上知道它有价值”，它必须有一个能真实落地的入口。

代码里对应的就是先枚举安全槽位，再检查该位置是不是基础塔，最后才升级：

```python
for site in PRODUCER_SAFE_SITES:
    x, y = SITE_LAYOUT[self.side][site]
    tower = self._tower_at(x, y, info)
    if tower is None or tower.type != TowerType.BASIC:
        continue
    cost = info.upgrade_tower_cost(int(TowerType.PRODUCER))
    if wallet >= cost:
        return [Operation(OperationType.UPGRADE_TOWER, tower.id, int(TowerType.PRODUCER))]
```

这个片段很关键，因为它把“生产塔不是随便转，而是只能在安全槽位和基础塔种子上转”写死了。这样做虽然保守，但能显著减少前线短命生产塔和无意义经济化。

#### 5.2.3 保持上限，并保护已建出的生产塔

`gf-v16` 没有把生产塔上限放大，而是继续把上限收在 1 个。我的判断是，当时主线还没有证明“一个生产塔可以稳定活到中盘并兑现收益”，直接加到多个会把版本从防线偏保守一下推到经济偏激进，风险太大。

同样地，生产塔建出来以后，`gf-v16` 在中盘前半段会尽量避免普通搜索和谨慎清算把它随手降掉或拆掉。因为如果每次资金紧一点就先卖生产塔，它就永远无法完成“先投入、后回收”的过程。

### 5.3 `Lightning Storm`：从救火技能改成节奏技能

在平台对局里，我很早就注意到强一些的 AI 往往不是只在基地危险时用 `Storm`。它们会把 `Storm` 放进一个持续节奏里：清理一段兵线、逼迫对方防守、给己方蚂蚁争取通过窗口。相比之下，如果我方一直把它拖成“非到特别值才放”，最后经常不是节省了 90 金，而是把整段中盘主动权让出去了。

`gf-v16` 对 `Storm` 的处理大致分成两类。

#### 5.3.1 压力型 rolling Storm

从中盘较早阶段开始，只要冷却和金币条件允许，AI 会尝试滚动 `Storm`。这一步不是固定打某个点，而是遍历合法落点并用 `forecast` 做比较。

比较时我重点看：

- 这发 `Storm` 能不能延缓己方掉血。
- 能不能减少敌方蚂蚁数量。
- 能不能对敌方基地形成真实压力。
- 落点是不是更靠近敌方半场，而不是把高价值技能浪费在收益很低的自家门口。
- 当前落点覆盖到的敌方蚂蚁密度是否足够。

也就是说，`Storm` 的选点不是只数“当前圈里有几只蚂蚁”，而是看它投下去以后，未来一小段时间的局面是不是更有利。

#### 5.3.2 收尾型 Storm

当敌方基地血量已经低，或者我方兵线已经压到一个适合终结的位置时，`Storm` 的使用会更偏进攻收尾。这个阶段的目标和普通防守不同：我不再只关心拖住己方基地，而是要把已经形成的机会兑现成敌方基地血量下降。

### 5.4 减少 `churn`：不是少操作，而是少无效操作

我在报告里保留 `churn` 这个词，是因为它确实概括了一个很烦但很真实的问题。这里的 `churn` 指防御塔反复建拆、降级、换位，导致资产没有稳定沉淀。

`gf-v16` 压低 `churn` 不是靠“禁止拆塔”这种硬做法，而是几层一起约束：

- 早中期不轻易开放回收型战术动作。
- 评价函数对回收折损记账。
- 空操作可以胜过边际收益很低的动作。
- 已建出的生产塔在中盘前半段受到保护。
- 候选塔位和塔位族减少了没有结构意义的换位。

这也是我觉得这个版本比前面更稳的地方。它不一定每局都打出最华丽的操作，但更少出现“忙了一百回合，发现自己只是把钱换成了一堆返还损耗”的情况。

## 六、平台对局复盘与版本迭代

### 6.1 我的验证方式

我在截止前的迭代不是只靠直觉改参数。更常见的流程是：

1. 把当前版本上传到平台。
2. 选择不同风格的其他 AI 做平台对局。
3. 下载对局回放和数据。
4. 看一批输局里哪些现象重复出现。
5. 只围绕最稳定的共性问题改一小步，再重新验证。

这种方式对我很有用，因为很多策略问题单看代码并不明显。比如“`Producer` 已经进候选了，为什么平台上还是没有生产塔”；再比如“`Storm` 不是完全不用，为什么节奏还是慢”。这些问题只有看实际对局过程，才能发现是入口没打通、预算被抢走，还是动作出现得太晚。

### 6.2 从前置版本到 `gf-v16`

`gf-v16`是在几轮平台复盘后收敛出来的版本。对我影响比较大的几步如下。

| 版本阶段 | 平台复盘中暴露的问题 | 我得到的结论 |
| --- | --- | --- |
| `gf-v10` 到 `gf-v14` | 生产塔候选存在，但实际对局里基本不走 `Producer`；首发和循环 `Storm` 仍慢于不少对手 | 只提高 `Producer` 评分不够，要让安全生产塔路线真正有入口 |
| `gf-v15` | 已经偶尔能转出 `Producer`，但频率和收益都不稳定；建塔多、升级少，说明金币还在被碎片动作消耗 | 问题从“有没有 Producer”转成“Producer 能不能活、钱能不能沉淀” |
| `gf-v16` | 收住生产塔数量，保护一个安全生产塔，同时减少无效 recycle，并提高中盘 `Storm` 周期 | 先把中盘骨架稳住，再谈更激进的推进机制 |

### 6.3 复盘中最关键的信号

在 `gf-v15` 之后继续做平台对局复盘时，我最关注的是下面几类信号。

| 观察维度 | `gf-v15` 暴露的问题 | 对 `gf-v16` 的影响 |
| --- | --- | --- |
| 经济 | `Producer` 已出现，但平均转化次数仍远低于对手；金币均值和高金币窗口偏少 | 不盲目扩生产塔数量，先保护一个稳定生产塔 |
| 防御塔 | 建塔动作偏多，升级偏少，说明资产沉淀不足 | 收紧早中期 recycle，强化稳定塔结构 |
| 超武 | `Storm` 平均次数偏少，中盘压制周期不够 | 下调 rolling `Storm` 的价值门槛，增加中盘出手机会 |
| 推进 | 己方蚂蚁贴近敌方基地的回合偏少 | 让生产塔、清兵和 `Storm` 形成更连续的压力链 |

如果只看一场输赢，这些现象可能会被对手风格掩盖；但在一批对局里它们反复出现，就说明要改的不是某个非常偶然的细节，而是版本的资源转化方式。

我当时最在意的几个具体数字是这些：

- `gf-v14` 的 11 局失败复盘里，`Producer` 升级次数是 0，对手平均约 5.9 次。
- 同一批对局里，`gf-v14` 平均第一发 `Storm` 在第 51.2 回合，对手在第 36.4 回合。
- `gf-v15` 的 11 局失败复盘里，平均 `Producer` 只有 0.55 次，对手约 8.09 次。
- `gf-v15` 平均 `Storm` 只有 3.27 次，对手约 6.36 次。
- `gf-v16` 的 10 局失败复盘里，平均第一发 `Storm` 约在第 65.8 回合，对手约在第 38.9 回合；`Producer` 虽然比 `v15` 更常出现，但存活回合还是偏少。
- 在 `gf-v16` 的这批对局中，我也看到了更明显的金币窗口差距：自己的平均金币大约 44.2，对手大约 73.2；90 金以上窗口也明显更短。

### 6.4 `gf-v16` 相对 `gf-15` 的具体改动

最后落到 `gf-v16` 上，改动并不是大规模重写，而是围绕“中盘资源链条”做收敛。

1. 已经建出的 `Producer` 在中盘前半段不再容易被普通搜索和谨慎清算拆掉。
2. `Producer pivot` 的出现条件适度放松，使安全生产塔更容易真实落地。
3. 生产塔上限继续保持为 1，避免版本从没有经济路线直接摆到经济过载。
4. 早中期回收动作更谨慎，减少低价值建拆和金币折损。
5. rolling `Storm` 的最低价值门槛下调，让中盘 `Storm` 周期更接近比赛需要的节奏。

这五条改动看上去不炫，但它们指向同一件事：让一个回合的资源选择能接到下一段节奏上，而不是每个回合各自合理、合起来却越来越散。

## 七、结果与分析

### 7.1 最终结果

我最终提交的是 `gf-v16`，公开比赛全局排名第 28 名。在人智导课程所有参加赛课结合的同学中，我的课内排名是第 9 名。

这个结果对我来说说明了两件事。第一，`greedy-forecast` 这种“明确战术层 + 小预算前瞻搜索”的路线是能在真实平台对抗中打出竞争力的。第二，它也没有强到可以忽略节奏细节，尤其是 `Producer` 兑现、金币窗口和 `Storm` 周期，只要其中一环慢下来，差距会很快被对手放大。

### 7.2 为什么最终交 `gf-v16`

在开发过程中，我当然想继续往后改，但最后提交版本并不是“编号越大越好”。我更关心的是哪一版在平台对局里表现更稳，且我能清楚解释它为什么这么打。

`gf-v16` 最终被我保留下来，主要是因为它在我当时的版本线里比较平衡：

- 它没有把主策略押在过多新机制上。
- 它已经把安全生产塔路线从“理论候选”推进到“真实动作”。
- 它比更早版本更重视减少无效建拆。
- 它把 `Storm` 重新放回中盘节奏，而不是只当偶发救火。

我不想最后交一个某几局很激进、但整体骨架还没站稳的版本。对这次课程作业而言，`gf-v16` 是我认为结果、可解释性和稳定性之间比较合适的选择。


## 八、我认为这个算法“聪明”的地方

课程要求里提到要说明为什么觉得自己的算法是聪明的。对我来说，`gf-v16` 的聪明不在于它用了一个听起来很大的名字，而在于它做了几件比较克制但有效的事。

第一，它没有把所有复杂度平均分配。真正关键的节奏动作被提到规则优先层，普通防线动作再交给搜索。这样既避免了纯规则写成死板脚本，也避免了纯搜索把预算浪费在大量不值钱的组合上。

第二，它不是只看静态分数。`forecast` 让候选动作接受未来局面的检验，特别适合 Antwar 这种“现在花钱，后面几十回合才知道亏不亏”的游戏。

第三，它承认经济动作有兑现期。`Producer` 不是一出现就马上赚，因此版本里必须有安全位、转型入口和中段保护，否则经济路线永远会被短期火力压过去。

第四，它把“不操作”也当成策略选择。比赛里很多弱动作的问题不是错得离谱，而是它把后面一个更强动作推迟了。愿意在边际收益低时停手，反而更接近我对节奏游戏的理解。

## 九、总结

这次 Antwar 作业让我最深的体会是：智能体设计不是把一堆机制堆上去就结束了，关键在于这些机制能不能在同一个节奏里工作。

`gf-v16` 最终形成的路线可以概括为：

- 用候选塔位和动作包控制搜索规模。
- 用 `forecast` 对短中期局面进行前瞻评估。
- 用评价函数同时关注防线安全、现金安全、塔结构和兵线压力。
- 用专门的 `Producer pivot` 打开受控经济路线。
- 用 rolling `Storm` 保持中盘超武节奏。
- 用回收限制和沉没成本惩罚减少无效 `churn`。

比起某一个参数本身，我觉得这次最有价值的是把“平台对局复盘 -> 找稳定问题 -> 小步改策略 -> 再回平台验证”的迭代链路跑通了。这个过程让我对复杂对抗环境中的智能体设计有了更具体的理解：一个能打的策略，往往不是最花哨的，而是它知道什么时候该算、什么时候该守、什么时候该攒，以及什么时候该把资源真正压到对手脸上。
